# 005 — 表格窄列被压到逐字竖排（列宽算法缺陷）

| 项目 | 值 |
|---|---|
| 状态 | fixed（待端到端复核） |
| 严重度 | 中（版面可读性；触发案例 1280 个表全部受影响） |
| 发现日期 | 2026-09-17 |
| 记录时 commit | `ef6e2a6`（修复前） |
| 修复位置 | `scripts/md2docx.js`：`consumeTable()` 的列宽分配段 |
| 触发案例 | `GMS-JD-SRS-V1.0.md`（1280 个八字段需求用例表） |

## 1. 现象

键值对型表格的**标签列过窄**，列内文字**逐字竖排**（每行只放得下一个字）：

```text
┌────┬──────────────────────┐
│ 需 │ 加载本地基础影像数据 │
│ 求 │                      │
│ 名 │                      │
│ 称 │                      │
├────┼──────────────────────┤
```

表头为「字段 / 内容」的两列表（如 `中文字体 / 字号` 对照表）同样出现。

## 2. 实测观测

触发案例中的需求表，首列实测：

| 指标 | 数值 |
|---|---|
| 首列宽 | 530 DXA = 9.3 mm |
| 扣除左右内边距（各 100 DXA）后可用 | 330 DXA = **5.8 mm** |
| 「需求名称」4 个中文字 @五号（10.5pt）需要 | 840 DXA = **14.8 mm** |
| 每行可容纳 | `floor(330 / 210)` = **1 个字** → 逐字竖排 |

## 3. 根因

原算法为「按内容权重等比分配 + 固定 8% 下限」，存在**两个**独立问题：

### 3.1 纯线性权重无法处理悬殊比例

同一张表里既有极短列（标签列，最长内容 4 字 = 权重 8）又有极长列
（「处理过程」数百字 = 权重 255），权重比达 **32×**。按比例分配时短列只该得：

```text
8844 × 8 / 263 = 269 DXA   （约 1.3 mm，远小于一个字）
```

### 3.2 8% 下限被「差值修正」循环击穿（真正的 bug）

下限本来能兜住（`8844 × 8% = 707`），但随后的舍入修正循环**对所有列一律 -1**，
不区分谁已触底：

```text
比例分配后(含下限): [ 707, 8533 ]   总 9240，超出页宽 396
差值修正：逐列轮流 -1 抹平 396
修正后:            [ 509, 8335 ]   ← 首列被削到 509 < 下限 707
```

该循环的本意只是抹平浮点取整的零星误差（正常几十 DXA），但此处需回收 396 DXA，
于是把已触底的列继续削薄——**下限形同虚设**。实测产物首列 530 DXA，与复现的 509
一致（差异来自实际权重取值）。

## 4. 修复（已实施）

改为**内容感知的三层分配**：

### 4.1 每列算「自然宽度」作为不可压下限

```javascript
const naturalWidths = colWeights.map(w =>
  Math.round(Math.min(w, READABLE_CAP_UNITS) * TABLE_HALF_UNIT_DXA * WIDTH_SAFETY) + CELL_PADDING_DXA);
```

- `TABLE_HALF_UNIT_DXA = SIZE.五号 × 5`：表格五号字，半角 105 DXA / 全角 210 DXA
- `READABLE_CAP_UNITS = 16`：**可读上限 8 个中文字**。内容短的列（标签）保住整词宽度；
  内容长的列只保一个适度地板——反正要折行，给再多也是浪费（这是"适应不同场景"的关键：
  不能把长列的最长内容当作不可压下限，否则内容列会独占大半页）
- `WIDTH_SAFETY = 1.08`：安全余量。中文全角理论宽 = 字号（210 DXA），但字体实际
  advance 可能略大且 Word 会内部舍入；若下限精确等于 `4 × 210`，标签会卡在换行
  边界，稍有偏差就退化成 3 字 + 换行。乘 1.08 后实测余量 1.2 mm，稳妥

### 4.2 迭代钉下限

先按权重分比例份额，凡份额低于自身下限的列「钉」在下限，剩余宽度只在未钉住的列之间
重新按比例分，重复至无新列触底。这样短列**刚好**拿到够写一个词的宽度而不过度占用
（对照：早先试过的"余量按权重补给所有列"会让 4 字标签列拿到 35.8 mm，白白多占 12 mm）。

### 4.3 舍入修正只从高于下限的列回收

```javascript
} else if (columnWidths[k] > floors[k]) {   // ← 原为 columnWidths[k] > 1
  columnWidths[k] -= 1;
```

触底列不再被削——修掉 3.2 的击穿 bug。

### 4.4 宽表保护（陷阱 7 不可破）

若下限总和已超页宽（如 33 位列宽表），按比例整体压缩下限，每列始终 ≥ 1 DXA，
避免负列宽使 docx 抛 `Invalid value '-N' specified. Must be a positive integer.`。

产物 XML 校验：首列单元格文字**未被拆成多段**（`<w:t>` 片段数 = 1）。

| 场景 | 权重 | 最窄列结果 | 判定 |

| 标准 4 列数据表 | 15:30:10:60 | 各列按内容比例 | ✅ |
| 6 列含窄列 | 4:8:63:51:6:10 | 窄列保住地板 | ✅ |
| 33 列宽表 | 均等 | 全为正、总和精确 | ✅ 陷阱 7 未破 |
| 2 列都极长 | 300 : 400 | 按比例分配 | ✅ |

## 7. 参数调优指引

若将来需要调整观感，改 `consumeTable()` 中三个常量即可：

| 常量 | 作用 | 调大 | 调小 |
|---|---|---|---|
| `READABLE_CAP_UNITS = 16` | 短列保护上限（16 单位 = 8 中文字） | 长内容列也保更宽地板，表格更"胖" | 短列保护变弱，可能重新逐字 |
| `WIDTH_SAFETY = 1.08` | 字宽安全余量 | 更保险不换行，略浪费宽度 | 节省宽度，但有换行风险 |
| `CELL_PADDING_DXA = 200` | 单元格左右内边距 | 更透气 | 更紧凑（须与 `buildCell` 的 margins 同步改） |
