# 004 — 缺分隔行的管道表格被当作普通段落

| 项目 | 值 |
|---|---|
| 状态 | fixed（待端到端复核） |
| 严重度 | 高（触发案例中 1280 个表格全部失效） |
| 发现日期 | 2026-09-17 |
| 记录时 commit | `0edb265`（修复前） |
| 修复位置 | `scripts/preprocess.js`：新增 `repairLooseTables()`；`scripts/md2docx.js`：空表头不输出表头行 |
| 触发案例 | `GMS-JD-SRS-V1.0.md`（1.4 MB，1280 个失效表格） |

## 1. 现象

Markdown 源文件中"看起来是表格"的内容，转换后**完全不是表格**：整块被压成
**一个普通段落**，所有单元格内容以 `|` 相连挤在一行里。

触发案例中，全文 1289 个管道块里只有 **9 个**是有效表格，其余 **1280 个全部失效**。

## 2. 最小复现

```markdown
| 需求名称 | 加载本地基础影像数据 |
| 需求标识 | GMS-JD-ZCCX-010 |
| 需求描述 | 三维场景应加载本地基础影像数据 |
```

转换后（实测）：`<w:tbl>` 数量为 **0**，正文出现一个段落：

```text
| 需求名称 | 加载本地基础影像数据 | | 需求标识 | GMS-JD-ZCCX-010 | | 需求描述 | ...
```

对照组（多一行分隔行）能正常成为表格：

```markdown
| 字段 | 内容 |
|------|------|
| 需求名称 | 加载本地基础影像数据 |
```

## 3. 根因

Markdown 表格语法**要求**表头行之后紧跟分隔行（`|---|---|`）。缺分隔行时
markdown-it 不会识别为表格：

```text
无分隔行 → paragraph_open → inline → paragraph_close   （整块一个段落）
有分隔行 → table_open → thead_open → … → table_close   （正常表格）
```

**这不是 md2docx 的解析缺陷，而是源文件缺少必需的语法成分。**
但需注意：源文件的写法并非作者手误，而是**生成器缺陷**——生成 md 用的技能
（`gjb438c-md-creator`）模板本身是**正确带分隔行**的：

```markdown
<!-- .agents/skills/gjb438c-md-creator/templates/srs-skeleton.md -->
| 字段 | 内容 |
|------|------|
| 需求名称 | [需求的功能名称] |
```

而实际产物把**表头行与分隔行一并丢失**，直接从 `| 需求名称 |` 开始
（实测 1280 个块中 1185 个紧跟 `######` 标题行）。即：**模板对、产物错**。

## 4. 决策：为什么在 md2docx 侧兼容，而不是改文档

| 方案 | 评价 |
|---|---|
| **改源文档** | 1280 处需批量补分隔行。文档来自外部生成器，**下次重新生成缺陷依旧**——只治标。且源文档在别的仓库/流程里，md2docx 无权修改。 |
| **改生成器技能** | 治本，但**不在本仓库**（位于 `gjb-work/.agents/skills/`），且已产出的存量文档仍需转换。 |
| **md2docx 侧兼容** ✅ | 存量文档立即可用；数据高度规整（见下），兼容风险可控；与项目既有"降级/补救"取向一致。 |

结论：**兼容**。同时建议生成器侧修复（另案，不属本仓库）。

## 5. 修复（已实施）

### 5.1 `repairLooseTables()`（`scripts/preprocess.js`）

对代码围栏外的连续 `|` 行块，若满足条件则**在块前补一个空表头行 + 分隔行**：

```markdown
|  |  |
|---|---|
| 需求名称 | 加载本地基础影像数据 |
| 需求标识 | GMS-JD-ZCCX-010 |
```

**为什么不把首行提升为表头**：这些块是"键值对"语义（需求名称 / 需求标识 / …），
若把首行当表头，`需求名称` 会变成加粗居中的表头，其值反而落进表头单元格——语义颠倒。
补**空**表头后由 md2docx 侧略去该行，结果是一张纯数据的两列表格，与作者本意一致。

**保守边界**（命中任一即不修复，避免误改）：

- 代码围栏内（含图表渲染失败降级出的 ` ```text ` 块）
- 已有分隔行（本就是合法表格）
- 不足 2 行、列数不一致、只有 1 列
- 块内含转义竖线 `\|`（切分不可靠）

### 5.2 空表头不输出表头行（`scripts/md2docx.js`）

`consumeTable()` 中，若所有表头单元格均为空文本，则整行不加入 `rows`，
避免出现一条无意义的空表头行（`tableHeader: true` 的跨页重复表头也一并避免）。

## 6. 验证

### 6.1 触发案例全量结果

`GMS-JD-SRS-V1.0.md`：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 识别到的表格数 | 9 | **1289** |
| 补全的表格数 | — | **1280** |
| 其中带表头行 | 9 | 9（原有标准表格） |
| 其中无表头行（补全的数据表） | 0 | 1280 |
| 成品大小 | 转换失败* | 4802.4 KB |

\* 修复前转换该文档时 PlantUML 大量失败，产物不可用。

**数据规整度实测**（这是兼容安全的前提）：1280 个块**全部**为 2 列 × 8 行，
列数分布 `{2: 1280}`、行数分布 `{8: 1280}`，**列数无一致例外**，
且全文转义竖线 `\|` 计数为 0、行内代码含 `|` 计数为 0。

### 6.3 与题注的次序依赖（重要）

`repairLooseTables()` 必须在 `markCaptions()` **之前**执行：表题注的判定依赖
"向下跳过空行后首个内容是表格行"（见 `AGENTS.md` Markdown 源文约定）。
若表格尚未修好，表题注会因为"下面不是表格"而漏识别。已按此顺序插入
（步骤 5.5，位于步骤 5 剥离列表编号之后、步骤 6 题注标记之前）。

## 7. 遗留

- **生成器侧修复**：`gjb438c-md-creator` 输出缺表头/分隔行，应在其产物生成阶段修正，
  否则每份新文档都要依赖本兼容。**不在本仓库，未处理。**
- 本兼容只处理"整块列数一致"的情形；若块内列数不一致（例如某行漏写一个 `|`），
  仍不会修复——那类情况无法可靠推断列边界，保守跳过是正确的。
